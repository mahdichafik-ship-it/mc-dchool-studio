The lightweight-preview architecture is accepted.

The remaining release blocker is now clearly identified:

The preview generator is still processing every burst image sequentially before IPC, so stale preview jobs accumulate.

Please implement ONE targeted change only:

NEWEST-IMAGE-WINS MUST APPLY BEFORE PREVIEW GENERATION, NOT ONLY IN THE RENDERER.

Required behavior:

1. Preserve every original capture
Every JPEG/RAW must still:
- be assigned to the correct student
- be persisted
- be paired correctly
- appear in the gallery
- remain available after restart

Skipping a LIVE PREVIEW generation job must never mean skipping the capture itself.

2. Coalesce pending live-preview generation jobs

If images A, B, C, D, E arrive while preview A is being generated:

- allow the current active preview job to finish if it cannot be safely cancelled
- discard/supersede pending preview jobs B, C and D
- generate preview E next

The live-preview queue should therefore contain at most:

- 1 active preview-generation job
- 1 newest pending preview-generation job

Do not allow a 10- or 50-image FIFO preview-generation backlog.

3. Separate preview generation from persistence

Every capture must still enter the persistence queue independently.

Example:

A B C D E captured

LIVE PREVIEW:
A → E

PERSISTENCE:
A → B → C → D → E

The photographer only needs the newest live image quickly.
The gallery/database still need every capture.

4. High priority for preview generation

The preview worker must remain higher priority than:
- original copy
- gallery work
- database enrichment not required for assignment
- cloud work

Do not let large background file copies compete with the newest preview unnecessarily.

5. Do not regenerate obsolete previews later

If B/C/D were superseded as LIVE previews, do not later create 1440px live-preview artifacts for them just because they were skipped.

For the gallery, generate smaller/lower-priority gallery thumbnails separately when needed.

Live-preview artifact generation and gallery-thumbnail generation should not be treated as the same job.

6. Keep Sharp/libvips

Do not go back to Jimp.

The current Sharp/libvips reduced-resolution path is acceptable.
