PHASE II APPROVED — IMPLEMENT ONLINE FIELD RECOVERY

The final photographer-group membership inspection is accepted.

Proceed with the ONLINE field-recovery implementation under the
following approved policy.

==================================================
1. AUTHORITATIVE PRODUCT RULE
==================================================

A person's Class/Group assignment and photographer group-photo
membership are separate concepts.

ORGANIZATIONAL ASSIGNMENT:

students.classId

represents where the student/person currently belongs.

PHOTOGRAPHER GROUP MEMBERSHIP:

groups
group_members

represents existing group-photo/capture/delivery relationships.

A Class/Group move changes ONLY organizational assignment.

It does NOT rewrite photographic history.

==================================================
2. EXAMPLE
==================================================

Ahmed currently belongs to:

Class A

Ahmed may already have:

- portraits
- Class A group-photo membership
- historical Class A group photographs
- delivery relationships

The photographer creates:

Class D

and moves Ahmed:

Class A → Class D

After the move:

ORGANIZATIONAL ROSTER

Class A:
Ahmed no longer appears.

Class D:
Ahmed appears.

BUT:

Do NOT automatically:

- remove Ahmed from the Class A photographer group
- add Ahmed to the Class D photographer group
- modify old group captures
- modify group delivery
- modify exclusions
- modify membershipDirty
- modify historical files

This is intentional.

==================================================
3. IMPLEMENT ONLINE ADD CLASS / ADD GROUP
==================================================

Enable:

+ Add Class

for school projects.

Enable:

+ Add Group

for corporate projects.

Use the existing classesTable architecture.

Flow:

Add Class/Group
→ enter name
→ validate
→ authenticated desktop request
→ server creates authoritative container
→ server returns ID
→ desktop stores/reconciles local class with cloudId
→ navigation refreshes
→ select new empty container

The new container starts EMPTY.

Do not automatically populate it.

==================================================
4. ONLINE REQUIREMENT
==================================================

Class/Group creation requires a verified online desktop connection in
this phase.

If offline:

Do not create a local-only container.

Show a clear message such as:

"Creating a new class requires a connection. You can continue
photographing the existing roster offline."

Corporate terminology should adapt appropriately.

Do not block existing offline photography.

==================================================
5. NAME VALIDATION
==================================================

Within the same project:

trim + case-insensitive comparison.

Reject duplicates such as:

Marketing
marketing
 MARKETING

Do not silently rename.

Same name in another project remains valid.

No schema migration is authorized.

If safe concurrent duplicate prevention cannot be implemented without a
schema/database constraint:

STOP before adding one.

Report the issue.

==================================================
6. RETRY SAFETY
==================================================

Creation must not produce duplicate containers because of an uncertain
network response.

Use the smallest safe retry mechanism available within the existing
architecture.

Do not introduce schema changes or a new generalized synchronization
framework.

If durable retry safety cannot be achieved without persisted
idempotency:

STOP and report that limitation.

==================================================
7. MOVE EXISTING PEOPLE
==================================================

For an existing or newly-created Class/Group, provide:

Add existing students

or corporate equivalent:

Add existing people

This opens project-wide selection.

The photographer can search/select people from multiple existing
containers.

Example:

Ahmed — Class A
Sara — Class B
Youssef — Class C

Destination:

Class D

Require explicit confirmation:

Move 3 students to Class D?

This is a MOVE, not a copy.

==================================================
8. MOVE OPERATION
==================================================

The server-authoritative move changes ONLY:

students.classId

Preserve:

- student/person primary identity
- generatedStudentId
- portraits
- capture records
- JPEG/RAW
- capture timestamps
- review state
- filenames
- upload records
- existing delivery relationships

Do NOT mutate:

- groups
- group_members
- groupMemberExclusions
- group_captures
- group_capture_files

Do NOT call reconcileDefaultGroups() as part of the move.

==================================================
9. ATOMIC BULK MOVE
==================================================

The selected move should be atomic.

Either:

all selected people move

or:

none move.

Validate before mutation:

- project exists
- project not finished
- destination belongs to project
- every selected person belongs to project
- no cross-project IDs
- valid desktop authorization

Do not leave a photographer with a partially moved selection after a
failed operation.

==================================================
10. LOCAL STATE ORDER
==================================================

SERVER FIRST.

For movement:

server validates
→ transaction commits
→ server responds
→ desktop updates/reconciles local students.classId
→ roster refreshes

If the server operation fails:

do not alter the local organizational assignment.
