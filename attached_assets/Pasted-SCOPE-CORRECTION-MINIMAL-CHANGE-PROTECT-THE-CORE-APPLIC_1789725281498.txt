SCOPE CORRECTION — MINIMAL CHANGE / PROTECT THE CORE APPLICATION

The inspection is approved as information, but I want to significantly
constrain the implementation scope.

Volume Capture v1.0.71 is currently our known-good production baseline.

The objective of this phase is primarily DESIGN / NAVIGATION.

DO NOT use this work as an opportunity to redesign the application
architecture.

==================================================

==================================================

PRESERVE THE CORE APPLICATION.

The existing working systems for:

- capture authority
- JPEG/RAW pairing

Do not refactor these systems.

Do not "clean up" nearby code.

Do not change architecture merely because another architecture might be

==================================================
2. USE THE EXISTING AUTHORITATIVE MODEL
==================================================

The inspection established that `classesTable` is already the
authoritative people container.

Use it.

SCHOOL:

CORPORATE:

→ Employees/People

DO NOT create:

- another people-container system
- parallel membership architecture

Do not repurpose the existing photographer `groupsTable` into the
primary navigation container.

==================================================
7. ADD CLASS / ADD GROUP
==================================================

We DO want the photographer to be able to create the appropriate
container from the sidebar.

School:
+ Add Class

Corporate:
+ Add Group

Use the existing classesTable.

New container:

- belongs to current project
- starts empty
- appears immediately under the project
- does not automatically copy people from another container

However:

IMPLEMENT THE SMALLEST SAFE SUPPORTING CHANGE.

The inspection found that desktop currently lacks authoritative class
create/rename/delete IPC.

Before adding anything, determine the MINIMUM handlers necessary for
the approved UI.

Do not redesign desktop/cloud synchronization as part of this phase.

In particular:

DO NOT invent a new offline class synchronization protocol yet.

DO NOT add new schema merely to support offline class creation.

If fully offline Add Class/Add Group cannot safely reconcile using the
current contracts:

STOP and report that specific limitation.

We can make that a separate architecture decision.

The priority of this phase is preserving the known-good application.

==================================================
8. UNIQUE NAMES
==================================================

Within ONE project, Class/Group/Department names must be unique.

Normalize using:

- trim
- case-insensitive comparison

Therefore:

Marketing
marketing
 MARKETING

are duplicates.

Reject duplicate creation.

Reject rename to an existing name.

Same name in DIFFERENT projects is allowed.

Do not silently create:

Marketing 2
Marketing Copy
Marketing-2

Show:

"A group named 'Marketing' already exists in this project."

or the school equivalent:

"A class named 'Class 2A' already exists in this project."

Prefer enforcing this in the smallest authoritative layer needed for
the operation.

Do not broaden the change into unrelated validation systems.

==================================================
9. DELETION — VERY IMPORTANT
==================================================

Class/Group deletion is NOT generally available once names have been
allocated.

A Class/Group may be deleted ONLY when:

- ZERO people are assigned
AND
- ZERO relevant capture/history dependencies exist.

If ONE person/name is allocated:

DELETE MUST BE BLOCKED.

If capture history exists:

DELETE MUST BE BLOCKED.

Do not cascade-delete students, employees, portraits or capture history
from this new UI.

IMPORTANT:

The inspection found that the CURRENT server class delete behavior can
delete a class and queue deletion of associated student/group photos.

DO NOT expose that destructive behavior through this UI.

Do not rewrite the entire deletion architecture during this phase.

Instead, either:

A. safely guard deletion according to the rule above with a minimal
   isolated change;

OR

B. if that cannot be guaranteed without broader core changes, leave
   Delete unavailable and report it.

Data protection is more important than having a Delete button.
